# DS-047: Make offline sync publication capability-safe during directory swaps

- **Status:** In progress
- **Priority:** P1
- **Scope:** Offline OSV synchronization / concurrent filesystem boundary

## Evidence

- DS-016 validates the sentinel-owned cache root and canonical `offline` child before lock acquisition and publication, and it uses open file handles for transfer and ZIP validation.
- Final temporary-file cleanup and publication still address the child by pathname. A process able to rename the `offline` directory and replace it with a symlink between validation and a pathname operation can create a time-of-check/time-of-use race.
- Detected swaps preserve temporary recovery files instead of following the changed namespace, but repeated path validation cannot make the remaining publication sequence race-free.

## Acceptance criteria

- Hold a capability or directory handle for the validated `offline` namespace and perform temporary-file creation, cleanup, backup, and final renames relative to that handle.
- A concurrent root/child rename or symlink swap cannot redirect reads, writes, removals, locks, or publication outside the sentinel-owned cache.
- Preserve the same-directory atomic replacement and pre-staged rollback guarantees from DS-016.
- Keep the implementation portable across supported Unix and Windows release targets, with explicit behavior where equivalent directory-relative APIs differ.

## Verification

- Pause a transfer after temporary-file creation, swap the root and `offline` paths, then resume; assert no external same-name file is read, overwritten, removed, or published.
- Repeat the race at validation, rollback staging, archive publication, marker publication, and handled-error cleanup boundaries.
- Run the filesystem race suite on Linux, macOS, and Windows along with the exact workspace Clippy command.

## Resolution

- Synchronization now opens the validated cache root and `offline` child as `cap_std` directory capabilities. The ownership sentinel is opened without following the final component, its identity is checked across the read, and root/child identities are retained for attachment checks.
- Lock creation, abandoned-temp enumeration and removal, archive and marker temporary creation, previous-archive reads, hard-link/copy rollback staging, final renames, restoration, and RAII cleanup are all relative to the held `offline` handle. No operation reconstructs an ambient child pathname after capability acquisition.
- Capability-owned temporary files keep the recognizable per-ecosystem suffixes needed for crash reclamation. Publication drops the open temporary handle and performs a same-directory relative rename; a marker failure restores the pre-staged archive, and a failed restore retains the last rollback copy instead of deleting it.
- Offline scans now open the archive and timestamp without following their final components relative to the same held `offline` capability. Both handles and their identities remain live through timestamp age validation and the complete ZIP walk; root, child, archive, and marker attachments are revalidated before a result can be returned.
- Path and identity revalidation remains as an early swap detector, but it is no longer the confinement mechanism. If a Unix rename lands after the last check, operations can affect only the original held directory. On Windows, directory handles commonly deny the rename; the cross-platform tests explicitly accept that denial or, where a swap is permitted, require the same capability confinement.
- Deterministic hooks exercise swaps after temporary creation and at validation, rollback staging, archive publication, marker publication, handled-error cleanup, lock creation, and abandoned-temp cleanup. Every test seeds same-name external archive, marker, lock, and temporary files and verifies that none is read, replaced, removed, or augmented.
- A deterministic offline-read hook separately swaps the cache root, `offline` child, archive, and marker after the original handles are open. The replacement is a fully valid external cache with an empty ZIP and current marker; successful swaps must fail closed instead of producing a clean scan, and denied Windows swaps must retain the original vulnerability result.
