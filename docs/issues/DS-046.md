# DS-046: Deliver and verify genuinely static Linux artifacts

- **Status:** In progress
- **Priority:** P2
- **Scope:** Release binaries / static-linking contract

## Evidence

- `Cargo.toml:58` configures `x86_64-unknown-linux-gnu`, which does not by itself satisfy the specification's single-static-binary constraint.
- Audit binary inspection found dynamic linkage to `liblzma`, `libbz2`, and `libiconv` in the current release build.
- Major upgrades such as `zip`/compression libraries can change native linkage, so this needs an artifact-level gate.

## Acceptance criteria

- Produce Linux targets whose supported baseline and static-linking definition are explicit (normally musl where feasible).
- Remove unintended dynamic native-library dependencies or document a consciously narrowed portability contract approved against the specification.
- CI inspects the shipped artifact, not just the build configuration, and fails on forbidden dynamic linkage.
- The binary runs in a minimal container without package installation or project runtime dependencies.

## Verification

- Inspect artifacts with `file`, `ldd`/`readelf` (or platform equivalents) and record the absence of unintended dynamic dependencies.
- Run the downloaded artifact in `scratch`/distroless or another agreed minimal environment and perform `--help` plus offline fixture scan.
- Verify checksum and compare the artifact version/source tag.

## Resolution

- Replaced the GNU Linux release target with explicit `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl` targets. Linux releases therefore have a static-musl contract and do not require glibc, a distribution package manager, or language/package-manager runtimes.
- Added a least-privilege static-Linux workflow with native x86-64 and ARM64 runners. It builds inside the official Rust 1.97.1 Alpine multi-architecture image pinned by digest, so each artifact is produced natively against musl rather than relying on an accidental host linker configuration.
- Added `scripts/verify-static-linux.sh`. The gate requires an executable ELF reported as statically linked or static PIE, rejects every `readelf` `NEEDED` entry, and executes the shipped binary's version and help paths. It therefore inspects the release artifact itself rather than inferring linkage from Cargo features.
- Each matrix job builds a `scratch` image containing only `depscan`, disables networking, makes the container filesystem read-only, and runs both `--help` and an offline Cargo fixture against read-only mounted inputs/cache. The binary and a SHA-256 checksum are then uploaded as the target-specific CI artifact.
- The container build output remains read-only to the unprivileged host runner. After artifact
  verification and the scratch-container smoke test, the workflow copies that exact binary into a
  runner-owned staging directory and writes the checksum there, rather than trying to mutate the
  root-owned bind-mounted Cargo target directory.
- Documented the two Linux targets and their runtime baseline in the README. macOS/Windows publication and the tag-driven GitHub Release remain explicitly owned by DS-045.
- Extended the tag-bound release acceptance matrix for both native Linux architectures. After the
  published archive's paired checksum and GitHub attestation are verified, the job inspects that
  extracted binary with `file` and `readelf`, then copies the same bytes into `scratch`. Version,
  help, and the exact four-package offline scan all run with networking disabled, a read-only root
  filesystem, and read-only fixture/cache mounts.
