# DS-038: Parse requirements options, includes, and extras correctly

- **Status:** Closed
- **Priority:** P1
- **Scope:** `requirements.txt` parser

## Evidence

- `crates/depscan-parsers/src/lib.rs:493-500` skips every line beginning `--` before checking `--requirement`, making that documented include form unreachable.
- Lines `507-523` split pinned/unpinned requirements ad hoc; hashes/options, extras, direct URLs, editable entries, continuations, markers, and option attachment can be misread as names or versions.
- Containment/security for includes is tracked separately in DS-017.

## Acceptance criteria

- Tokenize supported pip requirements-file syntax in the correct order, including `-r`/`--requirement` attached and separated forms, continuations, hashes, constraints/options, extras, markers, and direct/editable URLs.
- Only authoritative pinned registry requirements are enrichment-ready; ranges and non-registry sources carry accurate degraded/provenance state.
- Unknown dangerous/global options return actionable warnings/errors without becoming package names.

## Verification

- Add pip-compatible fixtures for each supported option/form, extras normalization, markers, hashes, continuations, URLs/editables, malformed lines, and both include spellings.
- Assert package coordinates and source files exactly.

## Resolution

- Requirements are parsed with `pep508_rs` rather than delimiter splitting. Names retain source spelling for display and PEP 503-normalized identity for providers; extras are separated from identity; exact `==` registry pins remain authoritative; and ranges/unpinned entries preserve raw and normalized PEP 440 constraints for `latest_matching`.
- Logical lines now apply unescaped continuations before pip-compatible comment removal. Per-requirement `--hash` and `-C`/`--config-settings` options are validated and removed before PEP 508 parsing.
- `-r`/`--requirement` and `-c`/`--constraint` accept short attached, separated, and long `=` forms before generic option handling. Constraint files pass through the same DS-017 containment, cycle, depth, file-count, and byte limits. Their PEP 440 bounds are intersected with matching requirements, contradictory exact pins fail visibly, and constraint-only names never become installed packages.
- Named direct URLs, legacy VCS `#egg=` editables, local artifacts, and bare archive URLs remain reportable but are non-enrichable. Alternate-index, `--no-index`, and `--find-links` directives conservatively disable public-registry enrichment for the whole requirements input.
- Supported pip options are handled explicitly. Candidate-policy options that cannot be represented by the freshness model disable range enrichment rather than inventing a match. Unsupported options and malformed requirements, hashes, constraints, continuations, or remote includes return source-file/line diagnostics; option values are not copied into errors.
- Environment markers are assumed true as required by the v0.1 specification and emit a warning containing only the source path and line number.

## Verification evidence (2026-08-19)

- The complete recursive fixture is accepted by pip 26.2.1 as 14 records (11 install requirements plus three constraints); depscan emits the 11 install coordinates, applies the matching constraints, and preserves the exact canonical source file for every included package.
- Parser fixtures cover all include spellings, constraints, global and per-requirement options, extras, markers, hashes, continuations, named URLs, VCS editables, local wheels, bare archive URLs, alternate indexes, and malformed/fail-closed forms.
