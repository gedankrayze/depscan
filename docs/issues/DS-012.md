# DS-012: Preserve uv/Poetry source, directness, and group provenance

- **Status:** Closed
- **Priority:** P1
- **Scope:** Python lock parsers

## Evidence

- `crates/depscan-parsers/src/lib.rs:421-457` routes uv and Poetry to one generic `[[package]]` parser despite different source/group schemas.
- Only a table-shaped `source.type` is inspected; uv source representations and Poetry metadata can therefore be misclassified.
- The parser never sets `direct` or `dev`, so `--direct-only` and `--no-dev` can discard or retain the wrong Python packages.

## Acceptance criteria

- Use format-specific uv and Poetry decoding with supported schema/version checks.
- Registry, git, URL, directory, editable, and path sources produce correct `enrichable` state and provenance.
- Direct/transitive and group/dev classification is derived when the lock/manifest makes it knowable; ambiguity is represented explicitly rather than guessed.
- `--direct-only` and `--no-dev` document and implement the resulting best-effort semantics.

## Verification

- Add current uv and Poetry fixture snapshots covering registry and non-registry sources, dependency groups, optional packages, and direct/transitive packages.
- Exercise CLI filters against those fixtures and assert the retained package set.

## Resolution

- uv schema version 1 and Poetry lock versions 1.0, 1.1, 2.0, and 2.1 now have separate, fail-closed decoders. Required package identities, PEP 440 versions, source shapes, uv dependency references, Poetry group/category metadata, and future schema versions return source-qualified errors instead of being skipped.
- uv directness and scope are derived from the project/workspace roots, manifest requirements, runtime edges, optional extras, and development groups. Graph traversal follows selected extras, production reachability wins over development-only reachability, and project/workspace packages are excluded from dependency results.
- Poetry uses lock category/group metadata for production versus development-only scope and joins sibling PEP 621, PEP 735, legacy Poetry, and named Poetry group declarations for directness. Poetry 2.0 locks generated without category/group metadata retain explicitly unknown scope; when the manifest is absent, directness remains explicitly unknown.
- Canonical PyPI registry packages remain enrichable. Alternate registries and uv/Poetry Git, URL, path/file, directory, and editable sources remain reportable but are never queried as PyPI registry coordinates; uv project/workspace roots are excluded from dependency results.
- `Package` now exposes `direct_known` and `dev_known`; JSON schema version 3 serializes both confidence flags. Duplicate-coordinate merges preserve uncertainty conservatively, `--direct-only` excludes only confirmed transitives, and `--no-dev` excludes only confirmed development-only packages.

## Verification evidence (2026-08-19)

- Current-format uv revision 3 and Poetry 2.1 fixtures snapshot registry, alternate-registry, Git, URL, path/file, directory, editable, optional, runtime, development-only, shared, direct, and transitive packages.
- Seven parser integration tests cover both snapshots, Poetry 1.1 category and real Poetry 1.8-style group-less 2.0 compatibility, current uv script-manifest extras, missing-manifest uncertainty, unsupported future schemas, malformed sources/groups/packages, missing or ambiguous dependency targets, and invalid PEP 440 versions.
- Three process-level CLI tests run offline scans against both fixtures and assert the exact `--direct-only`/`--no-dev` package sets, including retention of unknown Poetry directness and unknown uv development scope.
- Runtime probes parsed project/script locks generated by uv 0.12.5, a Poetry 2.3.2 lock, and a Poetry 1.8.3 group-less 2.0 lock through to the expected offline-provider boundary.
- `cargo +1.97.1 test --workspace --all-targets` and `cargo +1.95.0 test --locked --workspace --all-targets` each passed all 197 tests; `cargo clippy --all-targets -- -D warnings`, `cargo fmt --check`, and `git diff --check` passed.
