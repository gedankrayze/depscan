# DS-054: Resolve canonical NuGet identities from registration metadata

- **Status:** Closed
- **Priority:** P0
- **Scope:** NuGet registry enrichment / online OSV query planning / identity preservation

## Evidence

- [DS-003](DS-003.md) separated NuGet's lowercase internal and flat-container identity from the spelling sent to OSV, but it assumed that the spelling read from a project file was the canonical package ID.
- NuGet package references are case-insensitive, so a project may legitimately spell `Newtonsoft.Json` as `newtonsoft.json`; source-preserved casing is audit data, not registry-authoritative identity.
- A live OSV querybatch probe returned no advisory for `newtonsoft.json@12.0.1`, while the canonical `Newtonsoft.Json@12.0.1` coordinate returned `GHSA-5crp-9r3c-p9vr`.
- NuGet's flat-container version index contains only versions. The registration resource exposes the canonical package ID as `catalogEntry.id` for the concrete version being queried.
- Consequently, both exact and range-derived lowercased source references could produce false-clean online OSV results even though their internal identity and registry version lookup were otherwise correct.

## Acceptance criteria

- Keep NuGet's internal identity, deduplication key, registry cache coordinates, flat-container paths, and registration lookup paths lowercase and case-insensitive.
- Keep the exact package spelling read from the project visible and unchanged in every report.
- Represent registry-derived canonical identity separately from freshness data; do not rewrite the report package or overload `latest_stable`/`latest_matching`.
- For online NuGet scans, resolve `catalogEntry.id` from registration metadata for the exact installed version or, for a manifest range, the selected `latest_matching` version. Require that its normalized identity matches the requested package.
- Bound decompressed registration index and linked-page JSON responses. Reject malformed counts, missing or duplicate target leaves, missing or mismatched catalog identities, and non-inline page URLs outside the configured registration origin and package path prefix or containing credentials.
- Send online OSV only the validated canonical NuGet ID. If canonical identity cannot be established, leave vulnerability status visibly unresolved and never fall back to an uncanonicalized query.
- Preserve offline behavior: normalized NuGet dump matching must not require registration metadata or a registration cache entry.

## Verification

- Add provider tests for inline and linked registration pages, exact target selection, canonical `catalogEntry.id`, malformed/mismatched identities, same-origin/package-prefix URL confinement, and the decompressed response limit.
- Add query-plan tests proving online scans use an ephemeral canonical name without mutating the report package, omit an online coordinate when canonical identity is absent, and keep offline normalized matching independent of registration metadata.
- Add a process regression in which lowercase exact and range-derived source references can find an advisory only through the canonical OSV cache coordinate while reports retain the original lowercase spelling.
- Run the locked workspace/all-target suites on Rust 1.97.1 and 1.95.0, exact strict Clippy, formatting, RustSec, and diff checks.

## Resolution

- Registry enrichment now carries optional provider identity independently of `LatestVersions`. The online NuGet provider obtains that identity from the registration leaf for the concrete OSV target version while continuing to use lowercase flat-container and cache coordinates.
- Registration responses are fetched and parsed fail-closed under a 16 MiB decompressed limit. Linked pages are confined to the configured registration origin and lowercase package prefix; the selected leaf must have the requested NuGet version and a canonical `catalogEntry.id` whose normalized identity matches the source package.
- Online query planning writes the canonical ID only to its ephemeral OSV package clone. The original package name, display spelling, result key, exact version or manifest constraint, and range provenance remain unchanged in the report. Missing canonical metadata produces an explicit OSV-unresolved error and no uncanonicalized request.
- Offline planning retains ecosystem-normalized NuGet matching and has no registration metadata requirement.
