# DS-077: Move blocking cache locks and IO off the async runtime

- **Status:** Closed
- **Priority:** P1
- **Scope:** Provider cache concurrency (online registry and OSV paths)

## Evidence

- The 2026-08-21 code review found `Cache::lock_for` (`crates/depscan-providers/src/cache/store.rs`)
  taking a blocking `fs2` advisory lock on one shared per-namespace `.lock` file, with
  `put_if_unchanged` and `snapshot` performing blocking filesystem IO directly inside `async fn`
  bodies in `registry/client.rs`, `registry/sparse_client.rs`, `osv/client.rs`, and `osv/online.rs`.
- `crates/depscan-cli/src/app/scan.rs` drives up to 64 concurrent enrichment futures, so lock
  contention could park every tokio worker thread on one advisory lock and stall the whole
  runtime, including timers, instead of only the contending writes.
- The same crate already runs offline dump queries under `tokio::task::spawn_blocking`
  (`osv/offline.rs`), so the blocking calls were an inconsistency, not a design decision.

## Acceptance criteria

- No async provider path invokes the advisory cache lock or cache file IO directly on a runtime
  worker thread; the lock-read-compare-write critical section stays atomic under the lock.
- The synchronous cache primitives remain available for genuinely synchronous callers and tests,
  named per the crate's `*_blocking` convention.
- A regression test proves the runtime stays responsive while a cache publication waits on a
  contended advisory lock.

## Verification

- `cargo test -p depscan-providers`
- `bash scripts/dev-gate.sh full`

## Resolution

- Renamed the synchronous primitives to `Cache::snapshot_blocking` and
  `Cache::put_if_unchanged_blocking`, and added `pub(crate)` async `snapshot`,
  `put_if_unchanged`, and `get_if_fresh` wrappers that run them under
  `tokio::task::spawn_blocking`, mirroring the existing `OsvOffline::query_blocking` idiom. The
  entire lock-read-compare-write critical section still executes under the advisory lock, now on
  the blocking pool. A `spawn_blocking` join failure maps to `ProviderError::Cache` on the write
  path and degrades to a logged cache miss on the read paths.
- Converted every async call site: `RegistryClient::metadata_with_limit`,
  `RegistryClient::crates_metadata_for_index`, `OsvClient::publish_hydrated_document` (now an
  `async fn`), `OsvClient::hydrate`, and the OSV query cache path in `osv/online.rs`. The public
  synchronous `Cache::get`/`Cache::put` API is unchanged.
- Added `cache_publication_under_lock_contention_keeps_the_runtime_responsive`
  (`crates/depscan-providers/src/tests/cache.rs`): on a single-threaded runtime, a thread holds
  the namespace advisory lock for two seconds while an async publication waits; a concurrent
  50 ms tokio timer must complete in under one second. With the publication lock taken on the
  runtime thread instead, the timer stalls behind the lock and the test fails.

## Local verification evidence

- `cargo test -p depscan-providers`: 130 tests passed, including the new contention regression
  test; two hydration-publication tests were converted to `#[tokio::test]` for the now-async
  `publish_hydrated_document` and still pass.
- `bash scripts/dev-gate.sh full` passed on the frozen tree: architecture check (248 files,
  maximum 400 lines, tests isolated), automation and CI-policy verifiers, `cargo fmt --check`,
  `cargo clippy --all-targets -- -D warnings`, the full `--locked` workspace test suite, the
  GitHub Action and release workflow verifiers, and `git diff --check`.
- Native evidence covers macOS (this machine). Linux and Windows advisory-lock semantics run in
  the cross-platform PR quality matrix; both platforms block across same-process handles, which
  the regression test exercises.
