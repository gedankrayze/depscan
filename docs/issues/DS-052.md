# DS-052: Degrade unavailable Bun binary-lock extraction to manifests

- **Status:** Closed
- **Priority:** P1
- **Scope:** Bun detection / manifest parsing / optional tool orchestration

_Closed-record excerpts; original dates and versions apply._

## Evidence

- Specification section 3.1 requires a project with `bun.lockb` and no usable Bun executable to degrade to `package.json` manifest constraints and emit a warning.

- Detection selects `BunLockBinary` before `package.json`. Without `allow-tools`, the parser therefore returns a usage error even when a valid manifest is present.

- With `allow-tools`, a missing executable is also treated as an unconditional usage error. Root and workspace manifests are never considered, so the documented manifest-only mode is unavailable for this common legacy Bun layout.

## Historical resolution

- Binary Bun detection now has an explicit three-way boundary. Successful authorized extraction keeps resolved lockfile coordinates; disabled execution or a pre-start `Missing`/`Setup`/`Spawn` failure enters the manifest-only path; every failure after a process starts remains a usage/parse error.

- The manifest fallback requires a colocated root `package.json`, validates its JSON shape and dependency-section types, expands array and object-form workspace declarations only through contained relative patterns, validates every matched manifest inside the project root, and applies pattern/manifest-count bounds. Missing, malformed, escaping, or incomplete workspace inputs fail with source-qualified exit `10` diagnostics.

- Root and workspace production, development, optional, and peer dependencies retain exact `ManifestConstraint` values, declaring source paths, direct/development classifications, and `resolved_from_range=true`. Workspace/file/link/VCS/URL/alias descriptors remain visible but are not misrepresented as public npm coordinates.
