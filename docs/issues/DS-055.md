# DS-055: Fail hard when every manifest vulnerability coordinate is unresolved

- **Status:** Closed
- **Priority:** P1
- **Scope:** CLI registry-to-OSV orchestration / provider failure threshold

## Evidence

- `VulnerabilityQueryPlan` omitted every range-derived dependency whose registry lookup did not produce `latest_matching`, then passed an empty package list to OSV.
- Both OSV providers treat an empty input as a completed empty result because there is no eligible concrete coordinate on which to apply their total-failure threshold.
- A scan with two enrichable Cargo manifest dependencies, no registry cache, and all network access denied returned exit `0`, an empty vulnerability list, and only package-scoped errors. The existing offline process test encoded that false-clean exit.
- The development specification makes a single failed lookup soft but requires total provider failure to be hard with exit `30`.

## Acceptance criteria

- Return provider-hard-failure exit `30` when one or more registry-backed manifest dependencies were intended for vulnerability scanning and none resolves to a concrete OSV coordinate.
- Keep unresolved packages soft when at least one concrete coordinate remains queryable and produces a trustworthy result.
- Keep projects containing only non-registry/custom-source dependencies report-only; they do not constitute a failed public-provider scan.
- Never call either OSV provider with an empty plan that was produced solely by total manifest-resolution failure.

## Verification

- Add online and offline process cases with all enrichable manifest coordinates unresolved; assert exit `30`, no report, and a provider diagnostic.
- Add a partial case with one resolved vulnerable coordinate and one unresolved sibling; assert the finding remains reportable and the sibling retains an OSV error without promoting the scan to provider failure.
- Add an all-non-registry control that remains a clean report-only scan.
- Run the locked workspace/all-target suites on Rust 1.97.1 and 1.95.0, exact strict Clippy, formatting, RustSec, and diff checks.

## Resolution

- `VulnerabilityQueryPlan` now records how many consolidated packages were intended for registry-backed enrichment and exposes a total-resolution-failure state only when that count is non-zero and the concrete OSV plan is empty.
- Both online and offline orchestration reject that state before constructing the OSV provider call, returning a source-qualified provider hard failure. Concrete lockfile coordinates and partial manifest resolution continue through the existing DS-035 provider threshold.
- Report-only custom, Git, path, URL, and other non-registry dependencies do not increment the enrichable count and remain valid without registry or OSV state.
- The process matrix now covers online and offline total failure, one resolved vulnerable coordinate beside one unresolved sibling, and an all-non-registry project. Bun manifest-fallback tests seed registry metadata when they expect a completed offline vulnerability scan, preserving their original tool-authorization assertions under the stricter provider contract.

## Verification evidence

- Rust 1.97.1: `cargo +1.97.1 test --workspace --all-targets --locked` passed 323 tests; the opt-in live-provider test remained intentionally ignored.
- Rust 1.95.0: `cargo +1.95.0 test --workspace --all-targets --locked` passed the same 323 tests with the same intentional ignore.
- `cargo +1.97.1 clippy --all-targets -- -D warnings` and `cargo +1.97.1 fmt --all -- --check` passed.
- `cargo audit --file Cargo.lock --deny warnings --no-fetch` loaded 1,217 advisories and found no vulnerability or warning across 307 locked dependencies.
- `git diff --check` passed before commit.
