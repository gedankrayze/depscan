# DS-105: Evaluate suppression expiry independently of report reproducibility

- **Status:** Closed
- **Priority:** P1
- **Scope:** CLI suppression policy

## Evidence

`app/scan.rs` compares suppression expiry with `generated_at.date_naive()`.
`generated_at` comes from caller-controlled `SOURCE_DATE_EPOCH`. Backdating a
reproducible report therefore reactivates an already expired exception and changes
the security exit status. Future epochs can also expire an active exception early.

## Acceptance criteria

- Use the real scan UTC date for policy; use `SOURCE_DATE_EPOCH` only for report time.
- Add a process regression proving a backdated report retains an expired finding,
  its audit metadata, and exit 1.
- Document the distinction and retain reproducible-report tests.

## Resolution

- Suppression policy captures the real UTC scan date independently of the
  reproducible report timestamp. Only report metadata uses `SOURCE_DATE_EPOCH`.
- Added dedicated process tests for expired exceptions under a 1970 report epoch
  and active exceptions under a 2100 epoch. Updated the README policy boundary.

## Verification

- Both `suppression_time` process regressions pass: backdating retains the finding,
  expired audit metadata, and exit 1; future report time keeps a currently active
  exception suppressed with exit 0.
- Existing reproducibility and active/expired suppression tests pass in the
  release gate and Rust 1.96.0 locked all-target suite.
