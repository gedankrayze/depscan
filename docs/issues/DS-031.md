# DS-031: Implement exact retry and `Retry-After` semantics

- **Status:** Closed
- **Priority:** P1
- **Scope:** HTTP client reliability

## Evidence

- `crates/depscan-providers/src/lib.rs:194-240` loops over `0..3`, which is three total attempts rather than the specification's initial attempt plus three retries.
- `Retry-After` is parsed only as integer seconds at lines `222-229`; the valid HTTP-date form is ignored.
- A retry delay can be taken after the last available attempt, and byte downloads at lines `255-269` bypass retry handling entirely.

## Acceptance criteria

- Define and test the precise attempt budget (one request plus three retries) across JSON and streamed-byte paths.
- Honor both delta-seconds and HTTP-date `Retry-After`, capped to a documented safe maximum and driven by an injectable clock/sleeper.
- Retry only eligible connect/timeout/429/5xx failures with bounded exponential backoff and jitter; never sleep after the final attempt.
- Preserve the final error and request context without leaking response bodies/secrets.

## Verification

- Add deterministic mock tests for every retryable/non-retryable status, both `Retry-After` forms, attempt counts, cap, and final-attempt behavior.

## Resolution

- All ordinary JSON and bounded registry-byte requests now use one initial request plus three retries. Their fallback delays start at 200 ms, double for each retry, add up to 25% jitter, and cannot exceed 30 seconds. The same scheduler drives dump transfers, whose DS-016-specific transfer deadline, file streaming, restart-from-zero, and interrupted-body retry behavior remain intact.
- HTTP 429 and every 5xx status are retryable. Transport failures retry only when `reqwest` identifies a connection or timeout failure; other request-construction and response failures return immediately. A dump body interrupted after a successful response remains an explicit streaming-only retry case required by DS-016.
- `Retry-After` accepts delta-seconds and all three HTTP-date forms, computes dates against an injected clock, treats past dates as an immediate retry, and caps either representation at 30 seconds (or the dump's narrower test/configuration cap). Invalid values safely fall back to exponential backoff.
- The clock, sleeper, and jitter source are injected behind one retry runtime. Deterministic tests record every requested delay, proving four attempts produce exactly three sleeps and that no delay occurs after the final failure.
- Final failures retain the sanitized HTTP method, endpoint, status/failure class, and attempt count. URL credentials, query strings, response bodies, and request bodies are never copied into provider errors. The direct `httpdate` dependency is pinned to its current stable `1.0.3` release.
