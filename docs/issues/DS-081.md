# DS-081: Add a wall-clock deadline to OSV batch pagination

- **Status:** Closed
- **Priority:** P2
- **Scope:** OSV online provider

## Evidence

- The 2026-08-21 code review found `OsvClient::query_batch_outcomes`
  (`crates/depscan-providers/src/osv/client.rs`) bounded only by
  `OSV_MAX_QUERY_PAGES = 1_000` pages per query with a 10-second per-request timeout. A slow or
  adversarial server can keep one batch legitimately running for hours with no user-visible
  bound and no way to interrupt short of killing the process.

## Acceptance criteria

- A configurable or documented wall-clock deadline bounds one batch query end to end; hitting it
  surfaces as the existing per-package soft-failure path, not a hang or a false-clean result.
- The `sync` command's `--transfer-timeout` precedent is followed for naming and semantics.

## Verification

- A mock-server test where pagination exceeds the deadline and every pending package reports a
  provider error.
- `bash scripts/dev-gate.sh full`

## Resolution

- One batch query is now bounded by a documented five-minute wall clock
  (`OSV_QUERY_BATCH_DEADLINE`), checked between pagination round-trips; each in-flight request
  stays separately bounded by the ten-second HTTP timeout, so the practical bound is the
  deadline plus one request. Hitting it marks every still-pending package with a network
  failure that flows through the existing per-package soft-failure path — no hang, no
  false-clean result.
- A constant rather than a CLI flag: the deadline exists to make a pathological server
  interruptible, not to be tuned per scan; the issue's option to document rather than expose
  configuration is taken deliberately.

## Local verification evidence

- New mock test `batch_pagination_stops_at_the_wall_clock_deadline`: an endlessly paginating
  server is cut off by a short test deadline, the package reports a "pagination deadline"
  provider error, and pagination stops far below the page cap. All 132 provider tests pass.
