# DS-034: Make cache clearing safe for arbitrary configured paths

- **Status:** Closed
- **Priority:** P1
- **Scope:** Cache deletion / destructive filesystem safety

## Evidence

- `crates/depscan-providers/src/lib.rs:69-79` accepts `DEPSCAN_CACHE_DIR` as an arbitrary path and creates it.
- `crates/depscan-providers/src/lib.rs:138-142` passes that root directly to recursive `remove_dir_all`.
- `depscan cache clear` reaches it at `crates/depscan-cli/src/main.rs:456-462` without path ownership/sentinel validation or a broad-path guard.

## Acceptance criteria

- Cache initialization creates and validates a depscan-owned sentinel/version file.
- Refuse to clear filesystem roots, home/workspace roots, symlink targets, non-owned directories, empty paths, or other dangerously broad targets.
- Resolve the exact canonical target without following an attacker-swapped symlink and delete only known cache contents where practical.
- A refusal is explicit and leaves all data intact.

## Verification

- Add isolated tests for a normal owned cache plus `/`, a temporary home/workspace root, symlink swaps, missing sentinel, relative aliases, and a directory with unrelated files.
- Assert only the intended temporary cache tree can be removed.

## Resolution

- Cache roots now carry a strict, versioned `.depscan-cache.json` ownership sentinel. Arbitrary configured paths must either be empty or already have a valid sentinel; only the exact platform-default depscan cache may migrate a non-empty legacy layout containing exclusively the known cache namespaces.
- Initialization canonicalizes the requested directory and rejects empty paths, filesystem roots, home/workspace roots and their ancestors, VCS roots, final-component symlinks, non-directories, and non-owned non-empty directories.
- `cache clear` revalidates the canonical owned root and sentinel immediately before deletion. It removes only the `offline`, `osv`, and `registry` directories, refuses symlinked or escaped content targets, and preserves both the cache root and unrelated files.
- Refusal tests verify that missing/invalid sentinels, broad paths, root/content symlink swaps, and unrelated non-owned directories leave their data intact. A CLI process test verifies the sentinel and unrelated root files survive a successful clear.
