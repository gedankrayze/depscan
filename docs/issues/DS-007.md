# DS-007: Parse Bun text-lock locators correctly

- **Status:** Closed
- **Priority:** P1
- **Scope:** Bun parser

## Evidence

- `crates/depscan-parsers/src/lib.rs:221-246` treats the first element of a Bun package array as the resolved version.
- In current Bun text locks that element is a locator such as `name@1.2.3`, not the bare version required by the package model and providers.

## Acceptance criteria

- Parse the supported Bun lock schema explicitly and extract package name, resolved version, source, dev/directness, and workspace semantics correctly.
- Reject malformed locator arrays with a useful parse error; never send a locator string as the OSV version.
- Preserve scoped package names and aliases.

## Verification

- Add fixture snapshots from current Bun lockfile formats, including scoped packages, workspaces, aliases, and malformed entries.
- Assert all produced versions parse as the intended version model and contain no package locator prefix.

## Resolution

- The parser now validates Bun text-lock versions 0, 1, and 2 and their source-specific tuple shapes instead of treating an arbitrary array element as a version.
- Registry locators are split into the real npm package identity and a validated SemVer. Scoped names remain intact, while direct npm aliases are retained as the display name and use the underlying registry name for enrichment.
- Direct and development-only status is derived from every entry in the lockfile's `workspaces` object. A package used by any production, optional, or peer dependency is not marked development-only.
- Workspace, file, link, local/remote tarball, Git, and GitHub locators are validated but excluded from registry and OSV enrichment because Bun does not record a trustworthy npm package version for those sources.
- JSONC handling now supports line and block comments, escaped strings, and trailing commas without joining tokens or interpreting comment markers inside strings.
