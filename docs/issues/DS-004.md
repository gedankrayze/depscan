# DS-004: Use standards-compliant PEP 440 ordering

- **Status:** Open
- **Priority:** P0
- **Scope:** Core version logic / PyPI freshness

## Evidence

- `crates/depscan-core/src/lib.rs:300-305` routes PyPI versions to a hand-written fallback.
- `crates/depscan-core/src/lib.rs:331-385` consumes the remainder of the string after the first separator, so ordinary dotted releases can compare using only their first component.
- `Cargo.toml:44` already declares `pep440_rs`, but the comparator does not use it.
- Audit live evidence: `requests 2.32.5` was reported current while `2.9.2` was selected as latest; PyPI's audited latest was `2.34.2`.

## Acceptance criteria

- Use `pep440_rs` for parsing and ordering every PyPI version.
- Correctly handle dotted releases, epochs, pre/dev/post releases, local versions, and normalization.
- Latest-stable filtering follows PEP 440; prereleases are considered only when the installed version is itself a prerelease as specified.
- Staleness classification uses parsed release segments.

## Verification

- Add table-driven tests for `2.9.2 < 2.32.5 < 2.34.2`, epochs, `1.0a1`, `1.0rc1`, `1.0.post1`, and `1.0.dev1`.
- Add a PyPI provider mock containing out-of-order release keys and yanked/prerelease releases.
- Repeat the audited `requests` scan and assert `2.34.2` is selected when that remains the registry's latest stable.
