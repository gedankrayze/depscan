# DS-060: Make requirements include reads capability-safe

- **Status:** In progress
- **Priority:** P1
- **Scope:** Python requirements parser / concurrent filesystem integrity

## Evidence

- The parser performs pathname checks separately from use: it calls `symlink_metadata` and `canonicalize`, checks containment, and later reopens the canonical path with `File::open`.
- The opened handle is checked only for being a regular file. It is not proven to be the same file whose in-root identity was validated.
- A concurrent final-component, parent-directory, or scan-root replacement can redirect the later open outside the validated root. Parsed bytes then become package coordinates that can reach registry and OSV requests.
- This violates the README and DS-017 contract that every recursive requirements include is a regular non-symlink contained within the canonical scan root.
- Existing tests cover static escapes, symlinks, cycles, and limits, but not concurrent namespace replacement.

## Acceptance criteria

- Hold a capability for the validated requirements root throughout recursive parsing.
- Resolve and open the root file and every include relative to held capabilities; do not reopen a previously checked ambient pathname.
- Open final components without following symlinks, validate regular-file metadata from the opened handle, and read from that same handle.
- Preserve contained absolute includes and relative-to-including-file semantics without allowing parent or root replacement to redirect access.
- A replacement after opening must either leave reads bound to the original handle or produce exit `10`; outside bytes must never become package or provider fields.
- Preserve cycle detection, source provenance, include-chain diagnostics, and the existing depth, file-count, and total-byte limits.

## Verification

- Add deterministic barrier tests for final-file, include-parent, and scan-root swaps at resolution, open, and read boundaries.
- Exercise both symlink and regular-directory replacements; assert an outside sentinel is neither parsed nor exposed.
- Add a CLI process regression proving an unsafe swap exits `10` before any outside-derived provider request.
- Retain all DS-017 static containment and resource-bound tests.
- Run native platform coverage on Linux, macOS, and Windows, then the full workspace suite on Rust stable and MSRV plus exact Clippy.

## Resolution

- Requirements parsing now opens the detected file's parent once as a retained `cap-std` directory capability, proves its held identity against the canonical scan-root attachment, and resolves all recursive paths relative to retained capabilities. Requested-root and canonical absolute spellings map back to the same held root; other absolute paths and lexical `..` escapes fail closed.
- Every final requirements component is opened with no-follow semantics, checked as a regular file from that handle, read through that same handle, and then revalidated through freshly replayed root, directory-chain, and final-name capabilities before its bytes are parsed. Intermediate directory symlinks remain compatible only when capability-relative resolution proves they stay inside the root.
- Held identities use overlapping `st_dev`/`st_ino` handles on Unix and full `FILE_ID_INFO` volume plus 128-bit file IDs on Windows. The same identity model closes hardlink cycle aliases and detects regular root, parent, and final-name replacements without relying on ambient pathname equality.
- Existing canonical source provenance, relative-to-including-file behavior, include-chain diagnostics, active-cycle handling, and depth/file-count/byte limits remain in force. A successful post-acquisition namespace swap either stays bound to the original handles and is rejected during attachment replay or fails before bytes are parsed; replacement content never becomes package data.
- The CLI process regression uses a debug-assertions-only, exact stage/path/nonce barrier with a bounded timeout. Release builds compile out the hook. The regression proves a final-name race exits `10` with no report, no outside sentinel, and no cache/provider construction.

## Verification evidence (2026-08-20)

- On macOS, 19 focused requirements parser tests pass, including regular and symlink root/parent swaps, regular and symlink final swaps at file-open/before-read/after-read boundaries, hardlink cycles, requested-root absolute aliases, contained intermediate symlinks (including a nested sibling target that requires root-capability fallback), outside symlink rejection, and all retained DS-017 limits and diagnostics.
- Both focused requirements CLI process tests pass. The race test also proves a wrong nonce is inert and that rejected outside-derived input does not create the initially absent `DEPSCAN_CACHE_DIR`.
- `cargo +1.97.1 check -p depscan-parsers --all-targets --target x86_64-pc-windows-msvc --locked` passes, including the full-width Windows identity code and Windows case-insensitive component-boundary table. This is cross-compilation evidence only, not native Windows runtime evidence.
- `cargo +1.97.1 test --workspace --all-targets --locked` and `cargo +1.95.0 test --workspace --all-targets --locked` each pass 403 tests with 1 opt-in live-provider test ignored.
- Exact `cargo clippy --all-targets -- -D warnings`, `cargo +1.97.1 fmt --all -- --check`, and `git diff --check` pass on the final issue-scoped diff.
- Native Linux and Windows runtime coverage remains pending external CI. DS-060 therefore remains **In progress** rather than claiming the cross-platform acceptance criterion is complete.
