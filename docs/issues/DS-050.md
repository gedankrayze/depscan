# DS-050: Scan registry-resolved manifest dependencies for vulnerabilities

- **Status:** Closed
- **Priority:** P1
- **Scope:** CLI provider orchestration / degraded manifest-only vulnerability scanning

## Evidence

- Both online and offline OSV providers exclude every `Package` marked `resolved_from_range` because OSV evaluation requires a concrete version.
- The CLI invokes OSV before the registry provider, so it never turns the registry's `latest_matching` result into a concrete vulnerability query.
- Manifest-only exact and ranged dependencies can consequently receive freshness data while their vulnerability vector remains silently empty.

## Acceptance criteria

- Resolve enrichable manifest constraints through the native registry before vulnerability lookup.
- Query OSV with an ephemeral concrete coordinate using the newest matching published version, while retaining the original constraint, range flag, source, and package key in every report format.
- Map OSV findings and per-package provider errors back to the original report coordinate, including when multiple constraints select the same concrete release.
- In offline mode, use only acceptable cached registry metadata. When a manifest dependency cannot be resolved, add an explicit OSV error instead of presenting an unqueried dependency as confirmed clean.
- Never query public registries or OSV for dependencies already classified as non-registry or custom-source coordinates.
- Cover online-mode cache use and offline dump evaluation for exact and ranged manifests, including vulnerability exit `1`, report identity, and the missing-cache error path.

## Resolution

- The CLI now completes registry enrichment before invoking either OSV provider. Concrete lockfile and authoritative pinned coordinates continue to query directly.
- `VulnerabilityQueryPlan` turns only enrichable range-derived packages with a trustworthy `latest_matching` result into temporary concrete OSV coordinates. The report's original `Package` is never mutated, so its source constraint, normalized constraint, source file, range flag, and key remain auditable.
- OSV findings and soft errors are mapped from each temporary coordinate to every original constraint that selected it. Constraints selecting the same release share one provider query without losing either report result.
- A range with missing, stale, invalid, disabled, or non-matching registry metadata receives an explicit `osv` unresolved-status error in addition to the registry error. Non-enrichable custom-source packages are excluded from both registry and OSV plans.
- [DS-055](DS-055.md) subsequently made the total-failure boundary explicit: unresolved packages remain soft beside any trustworthy concrete query, but a scan where no intended enrichable manifest coordinate resolves is a provider hard failure with exit `30`.
- Focused process tests deny network access and prove the online provider/cache path and cached-registry/offline-dump path both find advisories for exact and ranged Cargo manifests, return exit `1`, and retain the original manifest identity. A separate offline test proves missing cache data is visible rather than false-clean.
