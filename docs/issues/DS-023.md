# DS-023: Implement explicitly allowed Bun and dotnet tool fallbacks

- **Status:** Closed
- **Priority:** P1
- **Scope:** CLI orchestration / optional external tools

## Evidence

- `crates/depscan-parsers/src/lib.rs:140-143` returns an error for binary `bun.lockb`.
- `crates/depscan-cli/src/main.rs:205-216` merely downgrades that error to a warning under `--allow-tools`; it never invokes Bun or obtains packages.
- `.NET` detection at `crates/depscan-parsers/src/lib.rs:579-593` has no `dotnet list package` fallback, and `allow_tools` is not used for .NET.

## Acceptance criteria

- Only when explicitly enabled, invoke Bun for `bun.lockb` textual extraction and dotnet for the specified transitive JSON fallback.
- Use fixed executable/argument arrays, controlled working directory/environment, timeouts, output limits, and no shell interpolation.
- Treat missing tools, non-zero exits, malformed output, and timeouts as actionable parse/provider outcomes rather than clean scans.
- Never execute a package-manager binary implicitly, including via config unless the user's effective setting authorizes it.

## Verification

- Add fake-executable integration tests that capture exact argv/cwd/env and return valid, malformed, oversized, failing, and hanging outputs.
- Assert tools are never started without `--allow-tools` (or its documented effective config equivalent).

## Resolution

- CLI orchestration now invokes only the two explicit fallbacks after the effective `allow-tools` decision: `bun bun.lockb` for a binary Bun lock and `dotnet list ./<project> package --include-transitive --format json --output-version 1 --verbosity quiet` for an unlocked .NET project. The `./` prevents option-like project names from changing the command, and offline .NET scans add `--no-restore`.
- The shared runner resolves a fixed executable from absolute `PATH` entries, uses a canonical project-directory working directory, clears and rebuilds a minimal environment around a temporary home, supplies null stdin, drains stdout and stderr concurrently under independent byte limits, and kills/reaps a command after ten seconds. It never interpolates a shell command.
- Tool stdout is passed to pure parser APIs. Bun output must be a valid Yarn Classic lock; dotnet output must be JSON schema version 1 for exactly the requested project, with valid framework, identity, resolved-version, and direct/transitive structures. Missing tools, non-zero exits, invalid UTF-8, malformed data, oversized output, and timeouts all fail as actionable parse/configuration outcomes rather than empty scans.
- Unix process-level tests use fake `bun` and `dotnet` executables to capture and assert exact arguments, canonical cwd, sanitized `PATH`, isolated home/temp variables, fixed control variables, and absence of an injected secret environment variable. They cover valid Bun and dotnet results, both malformed formats, over-limit output, non-zero exit, timeout, missing executable, explicit trusted-config authorization, and proof that CLI-disabled and implicit-config requests never start a tool.
