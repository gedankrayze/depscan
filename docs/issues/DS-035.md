# DS-035: Isolate partial OSV failures as per-package soft errors

- **Status:** Closed
- **Priority:** P1
- **Scope:** Online enrichment / error model

## Evidence

- `crates/depscan-providers/src/lib.rs:371-372` aborts the entire query on any chunk failure.
- Hydration collects all futures into one `Result` at `crates/depscan-providers/src/lib.rs:393-405`, so one advisory hydration failure aborts every package.
- `crates/depscan-cli/src/main.rs:235-245` maps any OSV provider error to a total scan failure, despite the specification defining isolated package lookup failures as soft errors.

## Acceptance criteria

- Attribute query-page and hydration failures to affected packages/advisories while returning successful results for unaffected packages.
- Promote to hard provider failure only when the provider is wholly unusable and no usable cache/result exists, with a documented threshold/decision.
- Never represent a failed package query as a clean empty advisory list or cache partial results as complete.
- Surface soft errors in `ScanResult.errors` and all relevant reports.

## Verification

- Add multi-chunk/multi-advisory mocks where exactly one chunk, page, or hydration fails and assert unaffected results remain complete.
- Add a total-outage case asserting exit `30` and partial cases asserting report visibility without false-clean cache entries.

## Resolution

- `VulnProvider` now returns a typed `VulnQueryOutcome` containing both the trustworthy vulnerability map and `Package::key`-scoped enrichment errors. The CLI merges OSV and registry errors into each package's `ScanResult.errors`; JSON and table output retain their existing visibility, summary output now includes the soft-failure count, and SARIF emits `DEPSCAN-PROVIDER-ERROR` warning results with package and provider properties.
- Query-batch parsing separates whole-response failures from aligned per-result failures. A failed chunk affects only that chunk; a later pagination request affects only queries still carrying page tokens; and a malformed aligned result does not discard valid sibling results. Revision lists are published to the query cache only after every page for that package completes, so accumulated IDs from an incomplete query never become a clean cache entry.
- Advisory hydration runs remain concurrent but are collected independently. Hydration failures are attributed to every package that referenced the advisory ID, while evaluation failures are attributed to the specific package/advisory pair. Successfully hydrated and evaluated sibling advisories remain reportable, and a failed hydration never creates a hydrated-document cache entry.
- Query and hydration cache publication is auxiliary to the current scan. A fully validated network result remains usable when serialization, locking, CAS publication, or filesystem I/O fails; the package retains the vulnerability result plus a visible cache warning. Query candidates are cached only after all pages complete, and a fresh canonical concurrent winner is preferred when cache reads are enabled.
- DS-051 superseded the earlier missing-`affected` exception after a later false-clean review. `affected` is now required as an array, package identities and other consumed fields are validated before filtering, and a query hit must have a matching evaluable entry. DS-035's partial-result and hard-failure thresholds remain unchanged.
- The hard-failure threshold is explicit: among enrichable packages with concrete resolved versions, at least one package must have a trustworthy usable result. A valid empty query is usable; a non-empty query is usable after at least one advisory hydrates and evaluates successfully, including a valid non-match. When every eligible package lacks such a result and no fresh cache supplies one, the provider returns a hard error and the CLI exits `30`. Otherwise affected packages carry visible soft errors and the scan continues.
- Offline dump scanning still returns a complete typed outcome and retains DS-030/DS-032's fail-closed age, archive, schema, and range-evaluation behavior.

- Provider mocks cover a failed 1,000-package chunk followed by a successful chunk, a later page failure after an aligned sibling completes, an individually malformed result, and mixed hydration/evaluation failures in a multi-advisory response. They assert package attribution and the absence of incomplete query or hydration cache entries.
- Deterministic unwritable query/hydration namespace tests prove that valid network results survive cache failure with package-scoped warnings. Present-but-non-array `affected` fixtures prove the sole malformed result fails hard without caching, while a valid sibling remains reportable and keeps the malformed advisory soft.
- Process tests deny all network access. With no usable OSV query cache the scan exits `30`; with one fresh completed query and one failed lookup it exits cleanly, emits the failed package's `osv` error in JSON, and does not create an empty query cache entry.
