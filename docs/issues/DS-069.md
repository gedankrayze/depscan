# DS-069: Classify Windows capability-lock swap denials exactly

- **Status:** In progress
- **Priority:** P1
- **Scope:** Provider capability-race tests / native Windows security evidence

## Evidence

- Native Windows jobs
  [96362737605](https://github.com/gedankrayze/depscan/actions/runs/32348643782/job/96362737605)
  and
  [96362750292](https://github.com/gedankrayze/depscan/actions/runs/32348647600/job/96362750292)
  each passed formatting and exact strict Clippy, then failed the same five provider capability-swap
  tests after reporting `ErrorKind::Uncategorized`.
- The swap helper retained only `io::Error::kind()`, losing both the failed operation and the raw
  Win32 code. Rust 1.97.1 does not map Win32 `ERROR_SHARING_VIOLATION` (`32`) to a named error kind,
  although that is the expected denial when an open directory capability omits
  `FILE_SHARE_DELETE`.
- Treating every uncategorized or raw OS error as an expected denial would let path, fixture, or
  second-stage replacement failures falsely satisfy the security regression.

## Acceptance criteria

- Retain the complete I/O error and distinguish original-name rename, symlink creation, and
  replacement-installation failures.
- On Windows, accept only raw sharing/access denial for the original rename and raw
  access/privilege denial for symlink creation. Reject neighboring, arbitrary, missing, and
  wrong-stage codes.
- Keep successful swaps fail-closed and external namespaces unchanged. When Windows prevents the
  swap, prove the original valid operation still succeeds or returns its independently expected
  invalid-input error.
- Do not enable `FILE_SHARE_DELETE`, broadly accept unknown errors, or weaken production
  capability confinement to make the attack simulation run.
- Pass the focused provider tests, full workspace tests, exact Clippy, formatting, and a native
  Windows quality job.

## Verification

- Run `cargo test -p depscan-providers --lib --locked`.
- Run `cargo test --workspace --all-targets --locked`.
- Run `cargo clippy --all-targets -- -D warnings`.
- Run `cargo fmt --all -- --check` and `git diff --check`.
- Record a successful native Windows full-suite rerun before closing.

## Resolution and evidence (2026-08-20)

- Denied outcomes now retain a phase-specific `NamespaceSwapStage` and the full `io::Error`.
  Diagnostics include the stage, mapped kind, raw code, and display text.
- The Windows classifier accepts only original-rename codes `5`/`32` and symlink-creation codes
  `5`/`1314`. A table regression rejects path-not-found `3`, lock-violation `33`, an arbitrary
  code, every replacement-installation denial, a sharing violation at the wrong stage, and a
  missing raw code.
- Denied-swap branches now assert the original sync, lock, acquisition, or vulnerable offline read
  remains semantically correct instead of treating denial alone as a passing result.
- The exact classifier regression passes `1/1`, the five capability-race filters pass `5/5`, and
  the complete provider library passes `129/129`. The Rust 1.97.1 workspace/all-target suite,
  exact all-target Clippy, formatting, and diff checks pass locally.
- The first corrected native Windows jobs
  [96370169472](https://github.com/gedankrayze/depscan/actions/runs/32351083090/job/96370169472)
  and
  [96370179346](https://github.com/gedankrayze/depscan/actions/runs/32351086533/job/96370179346)
  passed the phase/code classifier and the independently focused DS-070/071 regressions; the full
  provider suite then exposed one remaining DS-069 test-contract error in the combined
  cleanup-boundary case. When Windows denied the swap, the original invalid dump correctly
  produced its native `InvalidResponse`, while the test required a swap-detection `Cache` error.
  The assertion now distinguishes successful swaps from denied swaps and requires the original
  invalid-dump result, unchanged publication, and complete cleanup.
- DS-069 remains **In progress** until the corrected native Windows job passes.
