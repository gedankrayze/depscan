# DS-057: Reject malformed npm v2/v3 package records

- **Status:** Closed
- **Priority:** P1
- **Scope:** npm `package-lock.json` v1-v3 parser / false-clean prevention

_Closed-record excerpts; original dates and versions apply._

## Evidence

- The v2/v3 `packages` loop previously used `continue` for non-object values, malformed `node_modules` locations, and records with missing, empty, or non-string versions. A lock could therefore retain valid records, silently discard malformed ones, and produce a partial report that appeared clean.

- The realistic v2 fixture contained a `node_modules/missing-version` record, while the v3 fixture contained a non-object package record and malformed install locations. Their passing snapshots demonstrated that the omissions were accepted behavior rather than rejected input.

- npm v2/v3 package maps distinguish package locations from the legacy v1 recursive dependency tree. Treating arbitrary invalid locations as possible local metadata made that structural boundary ineffective.

## Historical resolution

- `parse_package_lock` now validates the complete v2/v3 package map before extraction. Every entry must be an object; optional `link` and `dev` fields are typed; and every link must name an existing descriptor object without carrying package dependency/name/version metadata. Installed-package targets remain scannable, while local descriptors are skipped only after link and workspace identity validation. Registry-looking links are rejected unless the target is a proven workspace with the same stable identity; npm's protected root workspace edge may override a later root alias, but non-root declarations must agree and their constraints must accept the linked workspace version.
