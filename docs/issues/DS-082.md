# DS-082: Remove the redundant enrichment concurrency limiter

- **Status:** Closed
- **Priority:** P2
- **Scope:** CLI scan enrichment

## Evidence

- The 2026-08-21 code review found `fetch_latest` (`crates/depscan-cli/src/app/scan.rs`)
  creating `Semaphore::new(64)` and acquiring a permit inside each future while
  `buffer_unordered(64)` already caps in-flight futures at the same limit. The semaphore can
  never be the binding constraint; its `.expect("semaphore closes only on drop")` exists purely
  to service the redundant layer.

## Acceptance criteria

- One limiter owns scan-level concurrency (per-ecosystem provider semaphores remain separate),
  and the accompanying `expect` disappears.

## Verification

- `cargo test -p depscan-cli`
- `bash scripts/dev-gate.sh full`

## Resolution

- Removed the semaphore and its `expect`; `buffer_unordered` now reads its limit from a named
  `MAX_CONCURRENT_ENRICHMENTS` constant with a comment pointing at the per-ecosystem provider
  semaphores that throttle further down. The unused `tokio::sync::Semaphore` import left the CLI.

## Local verification evidence

- `cargo clippy --workspace --all-targets` clean; all 25 workspace test suites pass.
- A live online scan matrix across npm, bun, PyPI, cargo, and NuGet projects after the change
  reproduced the pre-change package, vulnerability, and outdated counts.
