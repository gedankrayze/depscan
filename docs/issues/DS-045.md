# DS-045: Generate release automation and complete the target matrix

- **Status:** Closed
- **Priority:** P2
- **Scope:** Release engineering / artifact coverage

## Evidence

- `Cargo.toml:54-58` contains cargo-dist metadata, but the audited repository had no generated release workflow.
- The configured targets at `Cargo.toml:58` include only x86_64 GNU Linux, x86_64 macOS, and x86_64 Windows; ARM64 targets are absent.
- The specification requires GitHub Release artifacts and a cargo-dist-or-equivalent workflow, not metadata alone.

## Acceptance criteria

- Generate and review a pinned release workflow that builds, signs/checksums, and publishes supported artifacts from tags with least-privilege permissions.
- Add supported ARM64 targets for Linux/macOS (and Windows if support/testing is available), with an explicit documented platform matrix.
- Release jobs run quality gates and packaging checks before publication and produce installers promised by metadata.
- Checksums and provenance/attestations are published and tied to the exact source tag.

## Verification

- Run the release tool's plan/check locally and execute a non-publishing workflow dry run where possible.
- Create a test tag/release, download at least one artifact per target family, verify checksum/provenance, run `depscan --help`, and smoke-scan a fixture.

## Resolution

- Pinned cargo-dist 0.32.0 and every external release action to a full commit. A checked-in cross-platform installer selects only the five supported runner OS/architecture combinations, downloads the corresponding official cargo-dist archive, verifies its reviewed SHA-256 value before extraction, and rejects every other runner. No release job pipes downloaded content into an interpreter or executes cargo-dist's generated install command. Release tags are accepted only as strict semantic versions, enter shell steps through environment variables, and are passed to cargo-dist and GitHub CLI as quoted arguments; generated dependency/install/dist command strings are not executed. The generated tag workflow is read-only by default; only the host job receives `contents: write`, `id-token: write`, and `attestations: write`. `scripts/verify-release-workflow.sh` fails on a floating action, dynamic or pipe-to-shell bootstrap, missing reviewed checksum, direct GitHub-expression command interpolation, broadened or misplaced write permission, missing quality dependency, inherited quality-job secrets, or changed attestation action/scope.
- Enabled explicit SHA-256 output and host-phase GitHub artifact attestations. The release plan publishes and attests a source archive, shell installer, aggregate checksum, per-archive checksums, and Windows MSI/checksum alongside the five binary target archives. Homebrew output was removed before publication because no tap existed; the release must not advertise the broken `brew install depscan-cli` command.
- Added native Intel and Apple-silicon macOS targets to the two existing static-musl Linux targets and x86-64 Windows target. Windows ARM64 remains explicitly excluded because cargo-dist 0.32.0 does not list it as supported; runner availability alone is not artifact support or test evidence.
- Added a reusable, read-only release quality gate. Release artifact jobs depend on formatting, all-target tests, exact strict Clippy, verified workspace packaging, a locked release build, and `depscan --help` succeeding on Rust 1.97.1.
- Added the missing `dist` Cargo profile, inheriting the optimized release profile. A native artifact dry run first reproduced the otherwise hidden `profile dist is not defined` failure; after the fix, cargo-dist built the Apple-silicon archive and SHA-256 file successfully.
- Generated and checked in the Windows MSI definition. The CLI package now inherits the workspace author metadata required by WiX.
- Documented the complete target and installer matrix, the Windows ARM64 exclusion, and checksum/attestation verification commands in the README.
- Made the host phase derive the public filename set from the reviewed cargo-dist plan, require
  exactly those 16 files, and remove every phase's internal dist manifest before attestation or
  publication. Upstream cargo-dist publishes the plain host manifest as metadata by default; this
  repository deliberately narrows its public contract to the 16 reviewed source, installer,
  archive, MSI, and checksum deliverables. A single sorted checked-in filename contract is compared
  independently with both cargo-dist's pre-publication plan and the staged host directory, then is
  reused by post-publication acceptance so a changed 16-file plan cannot bypass review.
- The tag plan now peels the pushed tag and event revision, fetches public `main`, and refuses to
  publish unless that exact commit equals the current protected-branch tip. The plan exports that
  peeled commit instead of the possibly annotated tag-object event SHA. The host creates a draft
  with the complete reviewed inventory and publishes it only after every upload succeeds, matching
  GitHub's required ordering for immutable releases.
- Release runs serialize by ref without cancellation, and the host re-peels the remote tag both
  before draft creation and immediately before publication. Before `v1.1.0` is created, an active
  repository `v*` tag ruleset must block every update and deletion without a bypass actor; together
  these controls close the interval before publication makes the tag and complete asset set
  immutable.
- Added a manually dispatched acceptance matrix on the same five native target/architecture pairs
  as the cargo-dist plan. It peels the exact tag, proves protected-main ancestry and final release
  immutability, requires the 16 reviewed filenames, verifies every aggregate and paired checksum,
  authenticates all 16 files against tag-bound GitHub attestations, then runs each extracted
  binary's exact version, help, and four-package offline fixture scan paths. The first successful
  immutable-tag dispatch is recorded below.
- The shared release-asset verifier runs before attestation and draft creation as well as after
  download. It requires the exact 16-name contract, validates all seven paired records and payload
  bytes, and requires the aggregate checksum to name exactly the same seven distinct payloads.
  Malformed checksum metadata therefore cannot become immutable public state before detection.

## Local verification evidence

- Fresh downloads of all five official cargo-dist 0.32.0 runner archives matched the reviewed SHA-256 map, and each archive contained the expected executable path. The checked-in Unix installer independently downloaded and verified the Apple-silicon archive, extracted it only after authentication, and reported `cargo-dist 0.32.0`; the later v1.2.0 release run exercised the PowerShell path on native Windows.
- `dist generate --check`, `dist plan --tag v1.1.0 --output-format=json`, the release-workflow guard, `actionlint`, and `git diff --check` passed. The plan contained exactly the five documented targets and 16 source, installer, archive, MSI, and checksum artifacts after removing the unpublishable Homebrew formula.
- Rust 1.97.1 passed all 293 workspace/all-target tests and the exact `cargo clippy --all-targets -- -D warnings` command. `cargo package --workspace --locked --allow-dirty` packaged and verified all five crates after the release metadata changes.
- A non-publishing `dist build --artifacts=lies --tag v1.1.0` completed the entire artifact graph without creating a release. A real `dist build --artifacts=local --target=aarch64-apple-darwin --tag v1.1.0` produced an 8.3 MiB optimized executable in a 2.7 MiB archive. Its SHA-256 matched, the extracted binary's help succeeded, and a fresh-cache online scan of a copied Cargo fixture reported `2 packages | 0 vulns | 1 outdated`.
- The original local audit created no tag or GitHub Release. At that checkpoint, closure required an authorized tag whose commit
  equals the protected `main` tip at tag-plan time, cross-platform downloads from that release,
  checksum and provenance verification, extracted-binary startup, and fixture smoke scans. The
  later acceptance run permits `main` to have advanced but re-proves that the tagged release commit
  remains its ancestor. The v1.2.0 run recorded below satisfied that boundary; earlier green PR
  release quality and non-publishing static artifacts did not substitute for tag-bound evidence.
- The final pre-publication inventory review found that cargo-dist's default host phase preserves
  its own plain `dist-manifest.json` for publication, while the reviewed project plan and README
  promise 16 public deliverables. The hardened workflow intentionally excludes every phase
  manifest and compares the remaining staged filenames byte-for-byte with that 16-artifact plan
  before attestation and publication.
- The same pre-tag review downloaded cargo-dist 0.32.0's official Windows archive and proved it is
  flat. The unexecuted PowerShell bootstrap had incorrectly looked for a nested
  `cargo-dist-x86_64-pc-windows-msvc/dist.exe`; it now authenticates the same archive and selects
  root `dist.exe`, preventing the first Windows release job from failing before packaging.
- At the pre-tag audit, immutable releases were disabled and no tag ruleset existed. Both settings
  were treated as operational gates and configured before publication; the v1.2.0 acceptance
  preflight subsequently proved the immutable release and protected tag ancestry.
- Cargo-dist 0.32.0 still assigns the Apple-silicon build to `macos-14`, which remains available for
  this immediate release but entered deprecation on 2026-07-06 and is scheduled to retire on
  2026-11-02. Post-release acceptance deliberately uses the successor `macos-15` runner. Upgrade
  cargo-dist or override its build runner before that retirement; this maintenance boundary does
  not substitute for the first tag run recorded below.
