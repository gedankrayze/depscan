# DS-056: Reject future-dated reusable provider-cache entries

- **Status:** Closed
- **Priority:** P1
- **Scope:** Common provider cache / OSV and registry result integrity

## Evidence

- Common cache freshness subtracted `stored_at` from the current time and compared only whether the resulting age was within the TTL. A future timestamp therefore produced a negative duration that was smaller than every positive TTL and `--max-cache-age`.
- A deterministic process probe seeded an empty OSV query result and valid registry metadata with `stored_at` in 2099, denied all provider network access, and received exit `0`, no provider errors, and a clean vulnerability result. Even `--max-cache-age 1s` accepted the entry. The same scan with `--no-cache` exited `30` after the OSV request failed.
- The shared freshness bit controls online OSV query results, hydrated advisory documents, generic registry responses, crates.io sparse-index responses, and concurrent cache winners. `RegistryOffline` already rejected future timestamps explicitly, so changing only that path would leave the online false-clean behavior intact.

## Acceptance criteria

- Define common cache freshness against a controlled UTC time and require `stored_at <= now` before applying the provider TTL or a stricter `--max-cache-age`.
- Never count a future-dated empty OSV query, hydrated advisory, generic registry response, sparse-index response, or concurrent winner as a reusable result.
- Permit online providers to retain a future entry as the raw compare-and-swap generation and conditional-revalidation input, but require successful network validation or replacement before its value becomes reusable.
- Preserve cache-bypass semantics: `--no-cache` ignores reusable values while retaining the existing race-safe publication checks.
- Prove total OSV failure remains exit `30`, a failed future entry remains package-scoped beside a trustworthy result, and registry/sparse ETag revalidation can safely refresh a future timestamp.

## Resolution

- `Cache::lookup_from_entry_at` now classifies an entry as fresh only when its timestamp is at or before the supplied time and its non-negative age is within the effective TTL. The production wrapper supplies the current UTC time; the controlled helper makes exact-now, TTL-boundary, maximum-age, and one-nanosecond future behavior deterministic.
- All online provider consumers inherit that one decision. Future OSV query entries are refreshed instead of supplying clean results, future hydration entries require a network document, and future generic/sparse registry entries follow their normal conditional-revalidation paths.
- The raw entry remains available to compare-and-swap publication. A successful registry `304` rewrites its age at the current time, while an unvalidated future hydration document may remain on disk only as a non-reusable generation. Existing cache-bypass and concurrent-writer safeguards are unchanged.
- Process regressions deny every proxy: a sole future empty OSV result now exits `30` even under `--max-cache-age 1s`; beside a trustworthy fresh empty result, only the future entry's package receives a visible OSV error and the scan continues.
