# DS-058: Do not classify unproven Node dependencies as known transitive

- **Status:** Closed
- **Priority:** P1
- **Scope:** npm, pnpm, and Yarn lock directness and `--direct-only`

## Evidence

- Node manifest discovery is capped at five levels and silently discards traversal, read, and JSON parse failures in `sorted_project_files` and `node_direct_dependencies`.
- npm package-lock v2/v3 already validates root and workspace declarations and resolves them to concrete installed locations, but package construction ignores that evidence and derives `direct` only from separately discovered `package.json` files.
- pnpm similarly ignores lock importers and uses only the external manifest-name set; Yarn uses the same fallible manifest discovery.
- `Package::new` represents the resulting default as `direct = false` with `direct_known = true`. `--direct-only` therefore removes an actually direct package instead of retaining an unknown classification, contrary to the conservative filtering contract in the README.
- Lock-only npm parser fixtures already contain direct root declarations, but their directness assertions do not expose this false-negative path.

## Acceptance criteria

- For package-lock v2/v3, derive directness from validated root/workspace dependency edges and their resolved concrete install locations, including hoisted, nested, scoped, and aliased dependencies.
- Remove the arbitrary depth-five false-negative path; discover only validated project/workspace manifests where a separate manifest is required.
- When a format or missing/unreadable manifest cannot prove directness, set `direct_known = false` rather than known-transitive.
- Preserve known-transitive only when the lock/manifest relationship positively proves it.
- `--direct-only` includes proven direct packages, excludes proven transitives, and retains unknown classifications.

## Verification

- Add lock-only npm v2/v3 fixtures with root and workspace direct dependencies, including hoisting and aliases.
- Add a workspace manifest below the former depth limit.
- Add missing and malformed manifest cases for formats that require manifests, asserting `direct_known = false`.
- Add process-level offline `--direct-only` coverage asserting the exact proven-direct, proven-transitive, and unknown package sets.
- Run the full workspace suite on Rust stable and MSRV plus exact Clippy.

## Resolution

- npm package-lock versions 2 and 3 now derive directness entirely from the validated lock graph. Root and matcher-proven workspace dependency edges mark their concrete installed targets direct; traversal through installed-package edges proves descendants transitive. Installed records and disconnected installed subgraphs with no reachable declaration remain unknown. Alias, hoist, workspace, and duplicate-coordinate handling reuse the existing declaration-to-location binding, so identity/source validation and existential directness during deduplication remain intact.
- Manifest-dependent Node paths now inspect only the root `package.json` and manifests selected by its bounded workspace patterns. The root is read through its validated canonical path. Workspace manifest final components must be non-symlink regular files; each workspace path is canonicalized, checked for project containment, and retained for the subsequent read. These are bounded path and final-component checks rather than a claim of capability-based race immunity. The arbitrary depth-five directory walk and acceptance of undeclared nested manifests are gone. A successfully parsed declaration remains proven direct even if another declared workspace manifest fails, while an unmatched package is known transitive only when the complete bounded manifest set was established.
- Yarn declarations are bound to lock descriptor groups before packages are classified. A selector must resolve to exactly one lock entry; aliases and equivalent complete caret spellings are supported, while missing, malformed, unbound, or ambiguous evidence stays unknown. Yarn development scope is known only for a uniquely bound direct selector. pnpm v6/v9 directness now comes from exact importer `version` locators, including aliases, peer-qualified snapshots, and v6 document-level root groups; exact importer evidence also supplies the production/development scope. Otherwise pnpm preserves scope only when the package entry contains an explicit `dev` field, and leaves it unknown when that field and exact direct evidence are both absent. Unsupported or unmatched coordinates remain unknown instead of being guessed from names and SemVer ranges in a sibling manifest.
- Regression fixtures cover manifest-free npm v2 and v3 root/workspace/hoisted/alias edges, duplicate names, reachable transitives, and disconnected parent/child records; a declared workspace below the former depth limit; arbitrary nested manifests; static inside/outside workspace-manifest symlinks; Yarn selector normalization/mismatch/ambiguity, scope confidence, and partial manifest failure; and pnpm importer aliases, peer suffixes, alternate same-name versions, and scope confidence. The offline CLI regressions prove `--direct-only` retains Direct and Unknown records while excluding a proven transitive coordinate and `--no-dev` retains packages whose development scope is unknown.
